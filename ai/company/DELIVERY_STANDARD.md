# 交付标准

## 功能标准

1. 必须完成任务卡中的核心目标。
2. 不能破坏已有功能。
3. 不能引入明显临时硬编码。
4. 不能只改表面文案而不解决根因。
5. 不能绕过已有业务主链路、真实前端页面或真实数据口径。
6. 不允许为了通过测试而修改标准答案或降低验收标准。

## 代码标准

1. 修改范围要尽量小。
2. 命名要清晰，与现有项目语义兼容。
3. 错误处理要稳定。
4. 日志要保留排查信息。
5. 前端展示不能依赖不稳定的后端文案猜状态。
6. 后端不能把内部异常堆栈直接暴露给前端用户。
7. 复杂判断、兼容逻辑、降级逻辑必须写清楚中文注释。

## 测试标准

1. 能运行测试就必须运行测试。
2. 如果测试无法运行，必须说明具体原因。
3. 修改接口行为时，必须考虑接口测试、服务测试或回归样例。
4. 修改前端状态展示时，必须覆盖 success / empty / clarify / unsupported / error 等状态影响。
5. 修改物流或 BOM 问答能力时，不得破坏当前基线：物流真实网页 E2E `3281/3281`，BOM QA API E2E `30/30`，BOM 多问法回归 `129/129`。

## 报告标准

最终报告必须包含：

1. 本次目标。
2. 修改文件列表。
3. 每个文件改了什么。
4. 执行了哪些命令。
5. 测试是否通过。
6. 剩余风险。
7. 是否建议提交。
8. 建议 commit message。
