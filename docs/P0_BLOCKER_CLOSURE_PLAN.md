# P0 阻塞收口实施计划

## 一、文档目的

本计划只回答一件事：

> 在不进入第二业务域接入开发前，如何先收口平台主线里程碑 1.3 中识别出的 P0 阻塞。

本计划不包含代码实现，只包含：

1. 4 个 P0 阻塞的处理顺序
2. 每个阻塞的改动范围
3. 预期输出物
4. 验收标准
5. 风险点
6. 启动前置条件

---

## 二、当前背景

根据 `docs/PLATFORM_M1_3_BLOCKER_TRIAGE.md`，当前第二业务域接入前必须先收口的 P0 阻塞有 4 类：

1. `compare total-mode` 日志 `result_count` 可信度问题
2. direct query 与 `NL_QUERY` 的共享字段边界问题
3. 查询历史 / 回放最小快照基线问题
4. `fallback` 不是平台默认能力的边界说明问题

当前判断：

- 这些问题都属于平台共性层；
- 不收口会直接影响第二业务域复用；
- 但也都不需要升级成“大规模重构”。

---

## 三、推荐执行顺序

建议按以下顺序推进，而不是并行散打。

### 第一步：先定共享字段与快照基线

优先收口：

1. direct query 与 `NL_QUERY` 的共享字段边界
2. 查询历史 / 回放最小快照基线

原因：

- 这两项决定平台最小契约；
- `compare result_count` 和 `fallback 边界说明` 最终都要落回这个基线上；
- 如果不先定基线，后面修日志和补边界容易反复。

### 第二步：再修 `compare total-mode` 日志可信度

原因：

- 这是最明确、最容易形成可验证结果的 P0；
- 修完后可直接提升历史记录与审计可信度。

### 第三步：最后收口 `fallback` 平台边界

原因：

- `fallback` 不是优先扩功能，而是优先限制边界；
- 这一步应建立在共享字段和最小快照基线已经明确的前提上。

---

## 四、P0-1：direct query 与 NL_QUERY 的共享字段边界

### 1. 目标

明确平台层允许哪些响应轮廓并存，以及它们必须共享哪些字段语义。

### 2. 范围

本项只覆盖：

- `aggregate / detail / compare` direct query
- `NL_QUERY`
- 共享字段最小集合

本项不做：

- 把所有接口强行统一成一个完全相同的外形
- 前端 V3
- chat 接口统一

### 3. 建议处理方式

优先采用“统一共享字段语义，不强推单一外形”的方案。

建议明确两层：

1. 外层包装继续允许现状共存
2. 内层共享字段必须统一语义

建议先固化的共享字段最小集合：

- `status`
- `result_explanation`
- `no_result_analysis`
- `response_meta`
- `execution_mode`
- `query_type`
- `trace_id`

### 4. 预期输出物

1. 平台共享字段清单
2. direct query / `NL_QUERY` 轮廓对照表
3. 哪些接口必须补齐共享字段的改动清单
4. 对前端与历史详情的影响说明

### 5. 验收标准

至少满足：

1. 第二业务域接入时，不需要再猜“direct query 应返回哪些共享字段”
2. `aggregate / detail / compare / NL_QUERY` 的共享字段语义有书面结论
3. 前端结果卡片和历史详情可以基于同一共享字段判断状态与解释

### 6. 风险点

1. 若抽象过度，容易演变成接口大重构
2. 若只说原则、不落字段，第二业务域还是会重复兼容

### 7. 启动前置条件

1. `1.2` 的最小契约基线文档已确认
2. `1.3` 的 direct query / `NL_QUERY` 差异判断已确认

---

## 五、P0-2：查询历史 / 回放最小快照基线

### 1. 目标

把“平台可复用的历史 / 回放能力”从当前主要依赖 `NL_QUERY_PLAN`，提升为“direct query 也有最低可用快照”。

### 2. 范围

本项只覆盖：

- 历史列表最小字段
- 历史详情最小快照
- 回放最小可用结构

本项不做：

- 所有接口都做成与 `NL_QUERY_PLAN` 同等高保真
- 高级筛选继续扩展
- 大规模日志模型重构

### 3. 建议处理方式

先定义“最小快照基线”，而不是追求“一次性全量补齐”。

建议最小基线至少包含：

1. 请求侧：
   - `route_type`
   - `question_text` 或等价可读标题
   - 关键 payload

2. 结果侧：
   - `status`
   - `response_meta`
   - `query_result` 最小快照
   - `result_count`

3. 审计侧：
   - `execution_mode`
   - `trace_id`
   - `query_type`

### 4. 预期输出物

1. 历史列表最小字段基线
2. 历史详情最小快照基线
3. direct query 与 `NL_QUERY_PLAN` 的快照差异说明
4. 需要补齐的日志写入点清单

### 5. 验收标准

至少满足：

1. 平台不再只有 `NL_QUERY_PLAN` 才能称为“高价值回放”
2. direct query 日志至少具备可读、可判状态、可看结果摘要的能力
3. 第二业务域后续接入时，能复用同一套“最小历史快照”要求

### 6. 风险点

1. 如果追求一步到位补高保真，范围会迅速失控
2. 如果只补列表不补详情，回放价值仍然有限

### 7. 启动前置条件

1. 已明确共享字段最小集合
2. 已确认历史页和详情页当前真正依赖哪些字段

---

## 六、P0-3：compare total-mode 日志 `result_count` 可信度

### 1. 目标

确保总量 compare 场景下，日志里的 `result_count` 与真实业务结果一致，不再把“有值但 `items=[]`”误记为 0。

### 2. 范围

本项只覆盖：

- database compare total-mode
- 结果数量计算
- 历史日志可信度

本项不做：

- compare 解释丰富度增强
- compare 前端展示专项
- compare 全面契约重构

### 3. 建议处理方式

本项建议按“最小修复 + 回归锁定”执行。

建议具体动作：

1. 先确认 compare total-mode 的合法结果判定规则
2. 再统一日志层 `result_count` 计算口径
3. 最后补一条专门的回归测试

### 4. 预期输出物

1. compare total-mode 的结果计数规则说明
2. 日志写入修复点清单
3. 回归测试清单

### 5. 验收标准

至少满足：

1. total compare 场景历史记录中的 `result_count` 不再误记为 0
2. 历史列表、详情、回放不再基于错误数量做错误推断
3. 修复范围不外溢到 compare 解释专项

### 6. 风险点

1. 若把“结果数”与“明细行数”继续混用，容易再次回归
2. 若修复点分散在 service / repository / log service 多处，后续维护成本会高

### 7. 启动前置条件

1. 已明确 compare total-mode 的合法返回形态
2. 已确认日志写入链路位置

---

## 七、P0-4：fallback 不是平台默认能力的边界说明

### 1. 目标

把 `fallback` 从“默认可复用能力”降级为“logistics 当前兼容兜底能力”，明确第二业务域不能自动继承。

### 2. 范围

本项只覆盖：

- 平台文档说明
- 域接入规范
- fallback 启用边界
- 状态与提示语义

本项不做：

- fallback 全量语义清理
- compare fallback 能力扩展
- 第二业务域 fallback 实现

### 3. 建议处理方式

本项建议“先文档边界，后最小守卫”。

建议至少先明确：

1. fallback 仅属于 logistics 当前兼容能力
2. 第二业务域默认不启用 fallback
3. 若未来某域要启用 fallback，必须单独申明：
   - 数据来源
   - 语义可信范围
   - 状态展示方式
   - 是否进入历史回放

### 4. 预期输出物

1. fallback 平台边界说明
2. 域接入规范中的 fallback 条款
3. 第二业务域默认不继承 fallback 的书面结论

### 5. 验收标准

至少满足：

1. 文档中明确写清“fallback 不是平台默认能力”
2. 第二业务域接入规范中不再默认假设有 fallback
3. 后续评审时可直接据此判断某域是否允许 fallback

### 6. 风险点

1. 若只在口头说明、不写入规范，后续很容易再次被默认继承
2. 若边界写得太模糊，第二业务域仍会误用

### 7. 启动前置条件

1. `1.3` 中关于 fallback 的阻塞分级已确认
2. `1.2` 中域注册与接入规范基线已确认

---

## 八、建议的子里程碑拆分

建议把这轮 P0 收口拆成 3 个执行子里程碑，而不是 4 条并行推进。

### 子里程碑 A：共享字段与最小快照基线确认

覆盖：

1. direct query 与 `NL_QUERY` 的共享字段边界
2. 查询历史 / 回放最小快照基线

原因：

- 这是平台共性层的基础定义；
- 也是 compare 日志和 fallback 边界后续落地的参照系。

### 子里程碑 B：compare total-mode 日志可信度修复

覆盖：

1. total compare 的 `result_count`
2. 相关回归测试

原因：

- 修复点集中
- 验证标准清晰
- 能最快拿到“平台日志可信度”的可见改善

### 子里程碑 C：fallback 平台边界固化

覆盖：

1. 文档边界
2. 域接入规范补充
3. 必要的最小守卫策略说明

原因：

- 这一步更偏“边界治理”，放在共享基线之后做最稳。

---

## 九、建议的验收顺序

建议验收顺序如下：

1. 先验收共享字段与最小快照基线文档
2. 再验收 compare total-mode 日志修复
3. 最后验收 fallback 边界说明与规范固化

判断标准：

- 若第 1 步没有定清楚，不建议开始后两步编码；
- 若第 2 步未通过，不建议宣称“历史 / 回放已具备平台可信度”；
- 若第 3 步未固化，不建议进入第二业务域接入评审。

## 十、关于 plan_bom 字段字典的权威填写版建议

当前仓库里并不存在“两份并行维护的字段字典文件”：

- 现有实际文件只有：
  - `docs/PLAN_BOM_FIELD_DICTIONARY_TEMPLATE.md`
- 它当前已经从空模板升级成了“基于真实资料的初稿版”。

因此建议：

1. **直接把 `docs/PLAN_BOM_FIELD_DICTIONARY_TEMPLATE.md` 作为当前唯一权威填写版**
2. 不要再额外新建一份“空白版字段字典”给业务填写
3. 业务和数据侧应直接在这份初稿上补充、修正、确认

推荐理由：

1. 当前初稿已经包含真实样本里识别出的字段和映射线索
2. 若再发一份空白版，业务侧很容易丢掉已识别出的字段线索
3. 单一权威版本更适合后续做 Go / No-Go 重评

若后续确实需要保留“空白模板”，建议：

- 另建一份归档型文件；
- 但它只能作为示例模板，不能替代当前初稿版的填写主线。

## 十一、本轮结论

### 1. 当前最推荐的推进方式

当前最推荐的是：

1. 先做 P0 子里程碑 A：共享字段与最小快照基线
2. 再做 P0 子里程碑 B：compare total-mode 日志可信度
3. 最后做 P0 子里程碑 C：fallback 平台边界固化

### 2. 当前不建议做的事

当前不建议：

1. 直接跳到第二业务域接入开发
2. 把 P0 收口扩成大规模后端重构
3. 在 P0 未收口前再次扩到 RAG / 工具层 / Agent
