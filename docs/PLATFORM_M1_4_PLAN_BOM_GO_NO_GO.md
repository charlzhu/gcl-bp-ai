## 三、当前事实核查

### 1. 当前已经存在的内容

当前仓库里与 `plan_bom` 相关的真实内容，主要只有以下几类：

1. 域占位目录
   - `backend/app/domains/plan_bom/`
   - 当前只有一个 `__init__.py` 占位文件

2. 域路由关键词预留
   - `domain_keywords.yaml` 中已存在：
     - `BOM`
     - `物料清单`
     - `版本替代`
     - `替代料`
     - `计划BOM`

3. 占位模板
   - 当前仅有一个占位模板：
     - `plan_bom.aggregate.version_change_overview`
   - 模板名称为：
     - `BOM版本变更统计（占位模板）`

4. 多域框架预留
   - template loader
   - domain router
   - 多域测试样例

这些内容说明：

- 平台已经为 `plan_bom` 预留了“域识别”和“模板目录位置”；
- 但这只说明“平台骨架允许接入第二域”；
- **不等于计划 BOM 已具备真实启动条件。**

### 2. 当前缺失的关键输入

当前仓库内**没有发现**以下计划 BOM 启动所需的真实输入材料：

1. 数据源说明
2. 表结构说明
3. 字段字典
4. 核心业务规则口径
5. 最小问题集
6. 域负责人 / 资料归口人
7. 核心样例数据
8. 时间范围说明

### 3. 当前平台侧能支持到什么程度

如果只看平台能力，当前已经具备：

1. 多域关键词路由骨架
2. 多域模板目录骨架
3. 统一响应 / 状态 / 日志 / 回放的基线设计
4. logistics 作为样板域的可复用经验

但如果要真正启动计划 BOM，平台能力只是“必要条件的一部分”，还差“业务输入条件”。

## 四、计划 BOM 启动条件核查

以下按本轮要求逐项判断。

### 1. 数据源是否明确

结论：

**否。**

当前仓库中没有看到：

- 计划 BOM 数据源名称
- 数据库/Excel/系统来源说明
- 数据更新方式
- 是否存在历史与正式双源问题

判断：

- 这属于 **Go / No-Go 的硬条件缺失**。
- 没有数据源，就无法确认模板、查询模式和最小试点边界。

### 2. 表结构 / 字段字典是否明确

结论：

**否。**

当前仓库中没有看到：

- 计划 BOM 的表结构文档
- 字段字典
- 主键/版本号/替代关系/时间字段定义

判断：

- 这也是 **硬条件缺失**。
- 没有字段字典，就无法判断：
  - 适合走 `aggregate` 还是 `detail`
  - 哪些字段应进入模板槽位
  - 哪些字段应被提升为前端展示字段

### 3. 规则口径是否明确

结论：

**否。**

当前仓库中虽然有一个“BOM版本变更统计（占位模板）”，但没有看到与计划 BOM 相关的：

- 指标定义
- 维度定义
- 版本变更规则
- 替代料口径
- 生效时间口径
- 查询边界说明

判断：

- 这同样属于 **硬条件缺失**。
- 如果口径不清，第二域启动后会把“平台问题”和“业务定义问题”混在一起，无法有效验收。

### 4. 最小问题集是否明确

结论：

**否。**

当前仓库中没有看到计划 BOM 的：

- 10～20 条标准问题集
- 正常场景问题
- 空结果场景问题
- 明细或等价场景问题
- 预期答案或判断标准

判断：

- 这也是 **硬条件缺失**。
- 没有最小问题集，就无法做第二域试点验收，也无法复用当前物流域的回归方法。

### 5. 负责人是否明确

结论：

**否。**

当前文档中对域注册最小字段定义里提到了 `owner`，但并没有看到计划 BOM 的实际负责人、资料归口人或确认人。

判断：

- 这属于 **高优先级缺口**。
- 即使技术上能先接，如果没有业务 owner，后续规则确认、问题集确认和验收都会卡住。

## 五、Go / No-Go 结论

### 1. 当前结论

**结论：No-Go。**

### 2. 原因

当前计划 BOM 虽然具备“平台骨架预留”，但不具备“业务输入条件到位”的启动基础。

至少以下 5 项关键条件同时缺失：

1. 数据源不明确
2. 表结构 / 字段字典不明确
3. 规则口径不明确
4. 最小问题集不明确
5. 负责人不明确

这意味着：

- 现在如果直接进入计划 BOM 代码接入；
- 最终做出来的将不是“第二业务域试点”；
- 而是“在未知业务输入上做形式化接入”，风险很高。

### 3. 结论等级

本轮判断建议按以下等级理解：

- 不是“平台技术不支持”
- 而是“业务输入条件尚未达到可开工标准”

因此本轮 No-Go 的核心原因是：

> **不是平台骨架不够，而是计划 BOM 的真实输入尚未到位。**

## 六、缺口清单

若要把计划 BOM 从 No-Go 推进到 Go，至少需要补齐以下缺口。

### 1. 必须先补齐

1. 数据源说明
   - 来源系统
   - 更新方式
   - 时间范围
   - 是否存在历史 / 正式双源

2. 表结构 / 字段字典
   - 主表 / 明细表
   - 主键
   - 版本号字段
   - 替代料字段
   - 生效时间字段
   - 状态字段

3. 规则口径说明
   - 什么叫版本变更
   - 什么叫替代料
   - 时间口径怎么取
   - 哪些问题只允许查当前版本
   - 哪些问题允许查历史版本

4. 最小问题集
   - 至少 10～20 条
   - 覆盖正常 / 空结果 / 明细或等价查询
   - 有基本预期结果或判断标准

5. 负责人明确
   - 业务确认人
   - 数据确认人
   - 后续文档归口人

### 2. 建议同步补齐

1. 样例数据
2. 域注册信息草案
3. 支持的最小查询模式说明
4. 前端是否需要单独字段展示语义说明

## 七、若达到 Go，建议的最小试点范围

虽然本历史阶段结论是 No-Go，但为了后续准备，当时建议先预定义“达到 Go 后的最小试点范围”。

### 1. 建议的最小试点目标

仅验证：

- 第二业务域是否能接入平台骨架
- 统一响应 / 状态 / 日志 / 回放是否能复用
- 前后端是否能在不重做架构的情况下完成最小联调

### 2. 建议的最小业务范围

建议只做 **计划 BOM 的 aggregate 试点**，不要一开始就覆盖全量场景。

优先切片建议：

1. 单期版本变更统计
2. 单期替代料统计
3. 按月份或版本维度的基础聚合查询

暂不建议首批纳入：

1. 复杂 compare
2. 跨系统混合查询
3. 复杂明细回溯链路
4. 高度依赖口径解释的管理类问题

### 3. 建议的最小问题集结构

建议至少准备：

1. 正常聚合问题 6～8 条
2. 空结果问题 2～3 条
3. 明细或等价场景 2～3 条
4. 历史回放验证问题 2 条以上

### 4. 建议的最小验收目标

若后续达到 Go 并启动试点，最小验收建议是：

1. 域路由能正确识别到 `plan_bom`
2. 至少 1 个 aggregate 模板可真实执行
3. 返回共享字段符合平台最小契约
4. 查询历史可记录、可回放
5. 前端能完成最小查询与结果查看

## 八、历史阶段建议

### 1. 当前不建议做的事

本历史阶段不建议直接开始：

1. 计划 BOM 后端代码开发
2. 计划 BOM 前端页面开发
3. 为 plan_bom 新增大量模板
4. 为 plan_bom 做 RAG 或 Agent 设计

### 2. 当前建议先做的事

本历史阶段建议先补“输入条件”，不是先补“实现代码”。

优先顺序建议为：

1. 补齐计划 BOM 数据源说明
2. 补齐字段字典与规则口径
3. 补齐最小问题集
4. 明确业务 owner
5. 再进入第二业务域试点编码

## 九、本轮结论

### 1. Go / No-Go 结论

**历史阶段计划 BOM：No-Go。**
