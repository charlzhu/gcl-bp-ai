## 二、当前平台状态判断

### 1. 总体结论

当前仓库已经从“物流域单点能力搭建”进入到“可开始做平台主线收口”的阶段，但还没有进入：

- 多业务域稳定执行阶段
- 文档 RAG 实战阶段
- 工具层可调用阶段
- Agent 编排可落地阶段

当前更准确的判断是：

- **物流域查询能力：已完成并可前后端联调**
- **平台通用底座：已部分完成**
- **多域 / RAG / 工具 / Agent：大多仍处于预留或未启动状态**

| 能力项 | 当前状态 | 判断依据 | 结论 |

### 3. 当前平台状态的关键判断

当前平台最值得利用的资产，不是“目录里已经有几个空包”，而是：

1. **物流域已经形成了一条完整可运行样板链路**  
   这条样板链路包括数据、查询、解释、日志、前端展示、历史回放和回归清单。

   还没有经过第二业务域的真实落地验证。

3. **RAG、工具层、Agent 都还缺启动条件，不适合作为当前主线第一优先级**  
   当前仓库里没有真正的文档知识库链路，也没有工具调用协议，更没有 Agent 编排规范。

## 三、候选方向排序与推荐

### 1. 推荐方案

下一阶段最应该优先做的方向是：

**先做“继续物流域平台化 + 收口物流域剩余平台问题”，再以计划 BOM 作为第二业务域试点接入。**

### 2. 推荐排序

建议的主线优先级如下：

1. **继续物流域平台化，并收口物流域剩余平台问题**
2. **接入第二业务域，优先计划 BOM**
3. **工具层与 Agent 编排层的前置规范准备**
4. **物流文档知识库 / RAG 最小试点**
5. **经营分析、物料管理等更复杂业务域扩展**

### 3. 推荐理由

#### 方向 1：继续物流域平台化，并收口物流域剩余平台问题

推荐为第一优先级，原因是：

1. 当前真正跑通且前后端闭环完整的，只有 logistics。
2. 当前虽然已经有平台骨架，但大量核心能力仍然写成 logistics 专属实现。
3. 如果现在不先把 logistics 抽象成平台基线，直接上第二业务域，很容易复制出第二套“长得像平台、实际还是单域专用”的代码。
4. 统一响应契约、域注册信息、共用审计和回归方法，都应在这一阶段先沉淀成平台基线。

这意味着：

- **统一响应契约继续收口**，应该作为这个方向里的子任务；
- 而不是脱离平台化主线，单独当成一个独立大方向去做。

#### 方向 2：接入第二业务域，优先计划 BOM

推荐为第二优先级，原因是：

1. 平台是否真的具备扩展能力，必须靠第二业务域验证，而不是靠继续给 logistics 加细节验证。
2. 计划 BOM 相对更适合成为第一个试点域，能以较低风险验证：
   - 域路由是否可复用
   - 模板加载与命中机制是否可复用
   - 查询服务接口是否可复用
   - 历史 / 解释 / 回放链路是否可复用

#### 方向 3：工具层与 Agent 编排层前置规范准备

推荐为第三优先级，原因是：

1. 当前还不适合直接做 Agent，但需要提前沉淀“以后怎么接工具”的规范。
2. 真正的 Agent 编排必须建立在：
   - 明确的工具注册规范
   - 统一审计与留痕
   - 明确的执行边界

没有这些前置规范，后续直接做 Agent 会把平台带入无序扩展。

### 4. 为什么暂时不推荐把 RAG 作为主线第一优先级

当前不建议优先做物流文档 RAG，主要原因有三点：

1. **输入条件不充分**  
   还没有看到一套明确可用的物流文档台账、文档归属、有效版本、问答样例与评测题集。

2. **代码层只有预留，没有真正的知识库链路**  
   当前只有：
   - Milvus / LLM 配置项
   - 空的 `vector/` 与 `llm/` 目录

   没有：
   - 文档解析与切片
   - Embedding 入库
   - 召回服务
   - 引用展示
   - 评测闭环

3. **当前项目主价值仍然是结构化查询平台化**  
   现阶段更需要验证“一个域跑通后，平台如何复用到第二个域”，而不是把主线提前切到知识库问答。

### 5. 备选方案

如果下一阶段启动时发现：

- 计划 BOM 数据源尚未明确；
- 规则口径尚未整理；
- 试点问题集无法准备；

那么备选方案是：

**先完成“物流域平台基线抽象 + 工具层 / Agent 前置规范”两件事，再等待第二业务域输入条件成熟。**

但即使走备选方案，也仍不建议优先跳到正式 RAG 开发。

## 四、下一阶段里程碑设计

建议下一阶段平台主线按 **4 个里程碑** 推进。

### 里程碑 1：物流域平台基线抽象

#### 目标

把当前 logistics 从“单域可用系统”抽成“平台样板域”，明确哪些能力是平台共性，哪些仍然是域特有。

#### 范围

- 梳理并固化平台共性能力边界：
  - 域注册信息
  - 统一响应契约
  - 查询日志与回放结构
  - 回归清单标准
  - 域接入最小清单
- 收口物流域仍影响平台扩展的残留问题：
  - compare / fallback 的剩余风险确认
  - 跨域可复用字段和状态结构确认
- 产出“第二业务域接入规范草案”

#### 不做什么

- 不做前端 V3
- 不直接接第二业务域代码
- 不做 RAG
- 不做工具执行实现
- 不做 Agent 编排实现

#### 预期输出物

- 平台共性能力清单
- 第二业务域接入规范草案
- 统一响应契约基线说明
- 物流域平台样板说明

#### 风险点

- 过度抽象会把当前已稳定的 logistics 主链路打散
- 如果没有明确“平台共性”和“域特性”边界，容易反复重构

#### 启动前置条件

- 当前 V2 / V2.1 回归清单可稳定执行
- logistics 主链路已确认可作为平台样板
- compare / fallback 的高风险点已有清单化结论

### 里程碑 2：第二业务域试点接入（优先计划 BOM）

#### 目标

用第二业务域验证平台复用能力，而不是继续只在 logistics 域内自证平台化。

#### 范围

- 选择计划 BOM 作为首个试点域
- 明确该域的数据源、指标口径、维度口径、测试题集
- 完成最小查询链路打通：
  - 域路由
  - 模板识别
  - 最小 aggregate / detail 或等价查询能力
  - 历史记录与解释能力接入

#### 不做什么

- 不追求计划 BOM 全业务覆盖
- 不同时并行接入经营分析和物料管理
- 不做该域复杂前端专页

#### 预期输出物

- 第二业务域最小可执行链路
- 第二业务域测试题集
- 跨域路由与模板复用验证结果

#### 风险点

- 第二业务域若规则口径不清，会把平台问题和业务问题混在一起
- 若直接追求大而全，容易重新陷入“单域堆功能”

#### 启动前置条件

- 已有该域的表结构 / 字段字典 / 业务规则说明
- 已有至少 15～20 条可验收问题集
- 已明确该域的最小成功范围

### 里程碑 3：工具层与 Agent 编排前置规范

#### 目标

先把未来工具层和 Agent 的基础规范搭起来，但不直接做复杂实现。

#### 范围

- 定义工具注册规范
- 定义工具调用输入输出协议
- 定义工具执行审计与留痕结构
- 定义高风险动作的审批 / 禁止边界
- 明确哪些工具是真正下一阶段需要的：
  - 系统接口调用
  - 报表生成
  - Excel 计算
  - 发邮件

#### 不做什么

- 不真正实现完整工具库
- 不开发 Agent 多步编排
- 不做自动审批、自动执行闭环

#### 预期输出物

- 工具注册规范
- 工具执行审计结构
- Agent 前置约束说明
- 下一轮工具实现优先级列表

#### 风险点

- 过早设计复杂工具框架，容易脱离真实业务场景
- 如果没有明确的调用场景，规范会变成空文档

#### 启动前置条件

- 至少已有 2～3 个明确的真实工具需求场景
- 已明确哪些动作属于高风险、必须审计

### 里程碑 4：物流文档 RAG 最小启动条件达成后再试点

#### 目标

在输入条件成熟后，再启动物流文档知识库 / RAG 的最小试点，而不是把它提前当成平台主线第一步。

#### 范围

- 梳理文档清单与权威来源
- 明确版本、有效期、权限边界
- 准备问答评测集
- 最小文档入库、召回与引用能力

#### 不做什么

- 不做全公司知识库
- 不做复杂 Agent + RAG
- 不做没有出处的“泛回答”

#### 预期输出物

- 文档台账
- RAG 输入数据规范
- 最小评测题集
- 最小试点方案

#### 风险点

- 文档版本失控会直接导致回答不可信
- 如果没有评测集，RAG 质量无法验收

#### 启动前置条件

- 物流文档资料已经完整到位
- 已明确文档 owner、更新机制和有效版本
- 已准备基础问答评测集

## 五、第二业务域优先级建议

### 1. 推荐排序

建议优先级如下：

1. **计划 BOM**
2. **物料管理**
3. **经营分析**

### 2. 计划 BOM 为什么最适合先接

计划 BOM 适合作为第二业务域的原因：

1. **与现有查询服务框架复用性最高**  
   BOM 类问题天然更适合走：
   - 结构化查询
   - 模板匹配
   - 规则解析
   - aggregate / detail 式结果返回

2. **数据结构化程度通常高于经营分析口径型问题**  
   BOM 更容易有明确的：
   - 主数据
   - 版本号
   - 替代关系
   - 时间维度

3. **平台扩展价值高**  
   它能很好验证：
   - 第二域模板接入
   - 域路由
   - 共用解释与日志能力
   - 前后端复用路径

4. **实施复杂度相对可控**  
   相比经营分析，BOM 的指标和口径更容易先收敛出“最小成功切片”。

### 3. 物料管理为什么排第二

物料管理排第二，原因是：

1. 也具备较强的结构化查询潜力；
2. 但往往会更快触发：
   - 库存状态口径
   - 齐套 / 缺料规则
   - 多系统状态同步

这些问题比 BOM 更容易把平台主线拖进复杂业务细节里。

### 4. 经营分析为什么暂时排第三

经营分析排第三，原因是：

1. 口径复杂度通常最高；
2. 跨域、跨系统和财务口径更强；
3. 很容易出现“指标名看似简单，但定义高度依赖管理口径”的问题；
4. 当前项目还没有证明多域平台已经稳定，过早接经营分析风险最大。

### 5. 推荐结论

**下一业务域优先接：计划 BOM。**

推荐理由总结为一句话：

> 它最适合作为“第二业务域试点”，既能验证平台复用能力，又不会像经营分析那样过早把项目拖进高口径复杂度。

## 六、物流文档 RAG 启动条件判断

### 1. 当前是否已经适合马上启动物流文档 RAG

结论：

**当前还不适合作为下一阶段主线第一优先级直接启动。**

### 2. 当前已经具备的基础

当前可以视为“已具备最弱预留基础”的部分有：

- 后端配置里已有：
  - Milvus 连接配置
  - LLM 连接配置
- 项目目录中已有：
  - `backend/app/vector/`
  - `backend/app/llm/`

这些说明：

- 平台设计上已经考虑过 RAG 和模型接入；
- 但这只能算“预留接口位置”，不能算真正已具备 RAG 能力。

### 3. 当前不适合马上启动 RAG 的主要原因

当前至少还缺以下 5 类关键条件：

1. **文档输入条件缺失**
   - 文档清单不明确
   - 权威版本不明确
   - 更新机制不明确
   - 文档 owner 不明确

2. **技术链路缺失**
   - 文档解析
   - 切片与元数据设计
   - Embedding 生成
   - 向量入库
   - 召回服务
   - 引用输出

3. **评测条件缺失**
   - 缺少标准问题集
   - 缺少标准答案或判断标准
   - 缺少“正确引用文档”的验收方式

4. **业务边界缺失**
   - 哪些问题应走结构化查询
   - 哪些问题应走文档召回
   - 哪些问题必须人工确认

5. **前端展示边界缺失**
   - 引用块怎么展示
   - 文档来源怎么展示
   - 回答可信度怎么提示

### 4. 如果要启动 RAG，应该先补哪些最小能力

如果后续确认要做物流文档 RAG，建议先补的最小能力是：

1. 文档台账与文档来源管理
2. 文档解析与切片规范
3. 向量入库与基础召回服务
4. 引用与出处展示协议
5. 基础评测集

### 5. 推荐判断

当前对于物流文档 RAG 的推荐判断是：

- **不是“不做”**
- 而是 **“可以列入下一阶段后半程准备，但不应作为下一阶段主线第一步”**

## 七、下一阶段前置条件清单

下一阶段真正开工前，建议先确认以下输入条件。

### 1. 平台基线相关

- logistics 当前稳定主链路的回归结果
- 哪些响应字段必须上升为平台通用契约
- 哪些能力仍然只属于 logistics 域

### 2. 第二业务域相关

- 目标业务域是否已经明确
- 数据源是否明确
- 表结构 / 字段字典是否明确
- 核心业务规则与口径是否明确
- 是否已有标准测试题集

### 3. RAG 相关

- 文档资料是否完整到位
- 是否已有权威版本和管理责任人
- 是否允许进入向量库
- 是否已有评测题集

### 4. 工具层相关

- 是否已有真实工具需求场景
- 外部系统接口资料是否完整
- 哪些工具属于只读，哪些属于有副作用
- 是否已有审计要求

### 5. 平台治理相关

- `docs/NEXT_TASK.md`、`docs/CURRENT_STATUS.md` 等是否需要在下一轮统一刷新
- 是否需要把当前阶段性文档进一步整理成“历史阶段文档”和“当前状态文档”

---

## 八、风险与依赖

### 1. 最大风险

1. **把“目录预留”误判成“能力已具备”**  
   尤其是多域、RAG、工具层、Agent。

2. **第二业务域输入条件不足**  
   如果没有数据源、规则口径和测试题，第二域接入会沦为形式化接入。

3. **文档与当前仓库状态逐渐漂移**  
   当前已经出现“历史阶段文档”和“当前状态文档”并存的情况，后续若不治理，接手成本会持续上升。

### 2. 关键依赖

- 业务侧提供第二业务域最小规则与问题集
- 数据侧提供第二业务域最小数据源与字段字典
- 架构侧确认平台通用契约边界
- 文档侧确认 RAG 文档台账与有效版本

---

## 九、最终推荐结论

下一阶段平台主线的推荐结论是：

1. **先做物流域平台化抽象与剩余平台问题收口**
2. **再接第二业务域，优先计划 BOM**
3. **然后做工具层 / Agent 前置规范**
4. **最后在输入条件成熟后启动物流文档 RAG 最小试点**

一句话总结：

> 当前最应该做的，不是继续做前端 V3，也不是直接做 RAG 或 Agent，而是把 logistics 真正抽成平台样板，并用计划 BOM 验证平台能否走出第二个可执行业务域。
