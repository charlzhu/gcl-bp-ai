# 经营计划综合智能平台总体架构与阶段路线

## 一、文档用途

本文档用于沉淀《经营计划智能助手》从单业务域智能问答，演进为 **多 Agent 调控、多智能问答、多工具调用、第三方平台数据接入分析** 的综合智能平台的总体架构与阶段路线。

本文档回答以下问题：

1. 项目的长期产品定位是什么；
2. 平台应覆盖哪些业务域和问答类型；
3. 多 Agent、业务问答、数据计算、工具调用之间如何分层；
4. LLM、后端确定性代码、数据中间库、第三方平台各自承担什么职责；
5. 后续应按哪些阶段推进，避免过早进入失控 Agent 或自由 SQL；
6. 当前物管 SAP MID、计划 BOM、功率预测、物流 NL2SQL 等既有阶段文档如何纳入总路线。

## 二、总体产品定位

### 2.1 一句话定位

```text
本项目目标是建设面向经营计划场景的综合智能平台，
通过多 Agent 受控调度、多业务域智能问答、多工具调用和第三方数据接入，
覆盖物流、计划、物控/物管、经营分析四大业务域，
实现业务知识问答、确定性计算问答、综合分析问答和普通非业务问答，
并保证数据准确、过程可追溯、回答业务化、权限可控制。
```

### 2.2 核心能力组合

```text
经营计划综合智能平台
=
业务知识问答
+ 结构化数据问数
+ 确定性业务计算
+ 经营分析与归因
+ 多 Agent 受控编排
+ 多工具调用
+ 第三方平台数据接入
+ 普通非业务问答
+ 审计、回放、评测与权限治理
```

### 2.3 平台建设原则

1. **业务域清晰**：物流、计划、物控/物管、经营分析分域建设，避免单个 planner 或 service 被无限堆逻辑。
2. **LLM 不直接计算业务事实**：LLM 负责理解、拆解、归一化辅助和表达；后端确定性代码负责查数、计算、校验和追溯。
3. **用户问答不实时直查业务源库**：SAP Oracle MID、ERP、MES、WMS、TMS 等第三方平台应作为同步源或受控工具源；面向用户的问答优先基于智能助手中间库。
4. **多 Agent 必须受控**：Agent 可以调度任务和工具，但不得绕过白名单、权限、审计和阶段边界。
5. **工具调用可审计、可回放**：每次工具调用必须记录输入、输出、状态、耗时、错误、操作者和业务上下文。
6. **用户可见回答业务化**：回答中不得暴露 SQL、表名、字段名、query_key、planner、guardrail、schema、raw/debug、LLM 等内部技术细节。
7. **每个业务域必须有测试集**：业务问答能力必须有样例题、标准答案、回归脚本和验收报告，不能只依赖人工感觉。
8. **阶段边界优先**：当 `ai/inbox/requirement.md`、`docs/CURRENT_STATUS.md`、`docs/NEXT_TASK.md` 明确本轮只做某阶段时，不得自动进入后续阶段。

## 四、业务域总体划分

### 4.1 四大业务域

| 业务域 | 主要对象 | 典型问题 | 当前/后续重点 |
| --- | --- | --- | --- |
| 物流 | 发运、承运商、线路、区域、费用、车次、客户、项目 | “2024 年总运费是多少？”“哪个物流公司发运量最高？” | 巩固确定性 QA，推进受控 NL2SQL、复杂分析和跨年对比 |
| 计划 | 计划 BOM、订单、评审号、版型、客户实例、功率预测、产销存计划 | “这个 BOM 用了什么玻璃？”“该配置功率分布如何？” | 巩固 BOM 问答，完成功率预测计算引擎与 SAP BOM 数据源演进 |
| 物控/物管 | 库存、出入库、采购执行、工单组件、齐套、缺料、实际用料 | “某物料当前库存多少？”“下周排产是否缺料？” | SAP MID 同步到中间库，先做库存/出入库 MVP，再扩采购/工单/齐套 |
| 经营分析 | 产销存、预算、达成率、经营指标、趋势、异常归因 | “本月预算达成率如何？”“哪个部门指标异常？” | 建指标体系、口径字典、分析模型和管理层报告能力 |

> 命名说明：用户侧常说“物控”，当前文档中也出现“物管”。后续正式代码和前端入口应统一命名口径，建议在业务确认后决定是否展示为“物控”，内部域名可保持 `material_management`。

### 4.2 业务域边界原则

1. **物流域** 不承担计划 BOM、库存和经营指标计算。
2. **计划域** 可以调用 BOM、功率模型和计划相关数据，但不直接处理库存流水。
3. **物控/物管域** 承接库存、出入库、采购、工单组件和齐套，不新建割裂的 `sap` 业务域。
4. **经营分析域** 负责跨指标、跨部门、跨周期分析，但每个指标必须有确定性来源和口径。
5. 多域问题由总控层拆解，不允许某个业务域私自扩大查询边界。

## 五、问答类型分层

### 5.1 问答类型

| 类型 | 示例 | 处理原则 |
| --- | --- | --- |
| 普通问答 | “你是谁？”“帮我解释经营计划是什么” | 可直接由普通 LLM 闲聊/知识回答，仍需避免伪造项目事实 |
| 业务知识问答 | “BOM 里汇流条是什么意思？” | 优先来自业务文档、规则库、知识库或已确认口径 |
| 结构化查数问答 | “2024 年总运费是多少？” | 后端查中间库，确定性聚合，LLM 只表达 |
| 明细查询问答 | “列出某订单的 BOM 明细” | 受控 repository/service 查询，限制行数，支持展开/导出 |
| 计算回答 | “均价是多少？”“功率档位比例如何？” | 后端按固化公式计算，必须可追溯 |
| 综合分析回答 | “哪个承运商费用异常？” | 后端先出事实、指标、对比和异常候选，LLM 只能基于事实做业务化总结 |
| 多域复合问答 | “这个订单功率风险、库存齐套和物流成本如何？” | 总控 Agent 拆成多个受控子任务，再合并回答 |
| 澄清/拒答/无答案 | “吨位是多少？”但当前无吨位口径 | 缺口径则澄清，超范围则拒答，空结果不得自动放宽条件 |

### 5.2 LLM 与后端职责边界

| 环节 | LLM 可做 | 后端/程序必须做 |
| --- | --- | --- |
| 领域识别 | 给候选领域、置信度、理由摘要 | 白名单校验、低置信度澄清、多域拆分决策审计 |
| 意图识别 | 识别查询、计算、分析、普通问答等 | 映射到受控 query_key / capability / tool |
| 槽位抽取 | 抽取时间、实体、指标、维度候选 | 归一化、数据驱动候选解析、歧义消解、fail-closed |
| 复合问题拆解 | 语义判断是否可拆、拆成哪些子问 | 校验 source clause、子查询白名单、字段/单位/权限边界 |
| SQLPlan/QueryPlan | 生成结构化候选 | schema 校验、catalog 对齐、白名单、EXPLAIN、只读执行 |
| 工具选择 | 建议调用哪个工具 | 权限、参数、幂等、副作用审批、审计日志 |
| 业务计算 | 不直接计算最终事实数值 | 程序按固化公式和数据源计算 |
| 答案表达 | 业务化总结、解释、提醒 | 数值锁定、技术泄露检测、状态边界保护 |

## 七、多 Agent 受控调控设计

### 7.1 Agent 角色划分

| Agent | 主要职责 | 禁止事项 |
| --- | --- | --- |
| 总控 Agent | 判断领域、拆任务、选择业务能力、合并结果 | 不直接查库、不直接算业务事实、不绕过权限 |
| 物流 Agent | 处理物流指标、费用、线路、承运商、发运等问题 | 不处理 BOM、库存、经营指标 |
| 计划 Agent | 处理计划 BOM、订单、评审号、版型、功率预测、计划类问题 | 不直接查询库存源库，不绕过 BOM 消歧 |
| 物控/物管 Agent | 处理库存、出入库、采购、工单、齐套、缺料 | 不直接实时查 SAP Oracle MID 面向用户作答 |
| 经营分析 Agent | 处理经营指标、预算、达成率、趋势、异常归因 | 不编造指标口径，不跨权限拿数据 |
| 工具 Agent | 调用同步、报表、文件、第三方 API、通知等工具 | 不执行未注册工具，不执行未审批副作用动作 |
| 表达 Agent | 将确定性事实转成业务化自然语言 | 不新增事实、不改数值、不暴露技术实现 |

### 7.2 多 Agent 调度链路

```text
用户问题
↓
总控 Agent 识别：普通问答 / 单域业务问答 / 多域复合问答
↓
若单域：进入对应领域 Agent
若多域：拆成多个受控子任务
↓
每个领域 Agent 输出确定性结果或状态：success / clarification / unsupported / no_answer / error
↓
总控 Agent 合并结果，保留每个子任务状态和数据依据
↓
表达 Agent 生成业务化回答
↓
前端展示结论、明细、口径、风险和可追溯信息
```

### 7.3 受控 Agent 的必要约束

1. Agent 输出必须是结构化计划或受控调用，不是自由文本命令。
2. 所有可执行动作必须落到白名单 capability、service、repository 或 tool。
3. 多域拆解必须保留 source clause，能映射回用户原句。
4. 子任务不得依赖“上一步 LLM 猜出来的中间事实”，除非后端已物化并校验。
5. Agent 只能建议工具，工具执行层必须二次校验参数、权限和风险。
6. 涉及写入、同步、导出、外发、审批等副作用动作，应显式走审批或受控管理入口。

## 八、数据与第三方平台接入架构

### 8.1 数据进入平台的推荐方式

```text
第三方业务系统 / 文件 / API
  ↓
只读连接或受控导入
  ↓
ODS 原始落地层
  ↓
DWD 标准明细层
  ↓
DWS 主题汇总层
  ↓
DM 问答/分析结果层
  ↓
业务问答 / 分析 / 报表 / Agent 工具
```

### 8.2 第三方平台接入原则

| 原则 | 说明 |
| --- | --- |
| 只读优先 | SAP Oracle MID、ERP、MES、WMS、TMS 等外部系统优先只读接入 |
| 中间库优先 | 用户问答基于智能助手中间库，不实时直查业务源库 |
| 分层沉淀 | ODS 保留来源，DWD 标准化，DWS/DM 面向问答和分析 |
| 同步可追溯 | 每次同步记录批次、行数、耗时、错误、来源版本 |
| 幂等可重跑 | 重复同步不能产生重复脏数据 |
| 权限隔离 | 外部系统连接信息不得进入日志、文档、前端和提交记录 |
| 小步上线 | 先视图/主题 MVP，再逐步扩业务范围 |

### 8.3 工具调用分级

| 工具级别 | 示例 | 风险 | 执行要求 |
| --- | --- | --- | --- |
| L0 纯读工具 | 查中间库、查文档、查状态 | 低 | 白名单 + 日志 |
| L1 计算工具 | Excel 模型计算、功率预测、指标计算 | 中 | 固化公式 + 版本追溯 + 测试 |
| L2 同步工具 | SAP MID 手动同步、文件导入 | 中高 | 权限 + 幂等 + 审计 + 限流 |
| L3 导出/外发工具 | 导出 Excel、发送邮件/消息 | 高 | 人工确认或明确授权 + 水印/记录 |
| L4 写业务系统工具 | 反写 ERP/MES/WMS、审批提交 | 极高 | 当前阶段默认不做，未来需单独安全设计 |

## 九、统一 Query Planning 与受控 NL2SQL 路线

### 9.1 Query Planning V2 的定位

Query Planning V2 是跨业务域的统一规划 envelope，用于在正式检索、SQL 查询、RAG 查询或工具调用前，形成可审计、可回放、可测试的结构化计划。

它不是自由 planner，也不是让 LLM 直接接管查询，而是用于统一承接：

1. 规则 planner 结果；
2. LLM 候选理解；
3. query rewrite；
4. decomposition；
5. clarification；
6. no_answer / unsupported；
7. shadow 评估和灰度对比。

### 9.2 受控 NL2SQL 的定位

受控 NL2SQL 不是“LLM 直接写 SQL 执行”，而是：

```text
用户问题
↓
Query Rewrite / 领域路由
↓
Semantic Catalog 召回与 rerank
↓
LLM 生成 SQLPlan 候选
↓
后端校验 SQLPlan
↓
确定性 SQL renderer 或受控 SQL 候选
↓
sqlglot / 白名单 / 只读 / EXPLAIN / 试执行
↓
正式只读执行
↓
确定性事实
↓
LLM 业务化表达
```

### 9.3 先后顺序建议

1. 先用物流域验证 Semantic Catalog、SQLPlan、安全校验、EXPLAIN、shadow 一致性；
2. 只有核心 A 类问题达到高一致性后，才考虑小流量接管；
3. 再逐步扩展到计划 BOM、物控/物管、经营分析；
4. 对复杂计算型问题，例如功率预测、齐套缺料、预算达成率，应优先用确定性计算引擎，不应直接走自由 SQL。

## 十、知识库 / RAG 路线

### 10.1 RAG 适用范围

RAG 适合回答：

1. 业务制度、流程、术语解释；
2. 操作手册、字段说明、规则说明；
3. 历史交接文档、设计文档、验收报告；
4. 需要引用来源的非结构化知识问题。

RAG 不适合直接回答：

1. 需要实时/准实时数据计算的问题；
2. 需要严格公式计算的问题；
3. 需要从数据库聚合的业务指标；
4. 权限不明、来源不明、版本不明的业务事实。

### 10.2 RAG 启动前置条件

1. 文档台账完整；
2. 文档 owner、版本、有效期明确；
3. 允许入库范围明确；
4. 切片、元数据、权限、引用展示规范明确；
5. 有问答评测集；
6. 用户可见答案必须展示出处或数据依据。

## 十一、回答呈现与用户体验原则

### 11.1 用户可见回答结构

推荐业务回答结构：

```text
结论
↓
关键数据 / 关键配置 / 关键判断
↓
计算口径或分析依据摘要
↓
风险、异常或待确认项
↓
可展开明细 / 导出 / 查看数据依据
```

### 11.2 不同回答状态

| 状态 | 用户体验 |
| --- | --- |
| success | 直接给业务结论和关键数据 |
| clarification | 说明缺少哪个业务条件，并给可选项 |
| empty_result | 说明当前条件下无数据，不自动放宽筛选 |
| unsupported | 说明当前能力/数据/口径暂不支持，并给可改问建议 |
| error | 说明系统处理异常，不暴露堆栈、SQL、表名和内部字段 |
| partial | 多域问题中部分子任务成功、部分需澄清或暂不支持时，分块展示 |

### 11.3 技术泄露红线

用户可见内容不得出现：

```text
SQL、表名、字段名、query_key、planner、guardrail、schema、raw、debug、trace、LLM、embedding、rerank、Milvus collection、内部接口路径、真实连接信息
```

内部审计可以保存这些信息，但必须与用户展示隔离。

### 阶段 P4：统一业务问答入口与多域路由

### 阶段 P5：工具注册、工具调用与审计框架

目标：建设多工具调用的基础设施，但先从只读和中风险工具开始。

### 阶段 P6：多 Agent 受控编排

6. 建立多 Agent 回归测试集。

1. 每个可执行子任务都有确定性 service/tool 承接；

3. 多 Agent 不能绕过业务域边界；

### 阶段 P7：经营分析与主动智能

目标：从被动问答升级到经营指标分析、风险预警和管理建议。

重点任务：

1. 建立经营分析指标体系和口径字典；

3. 建立趋势、对比、异常检测和归因候选；
4. 生成周报/月报/专题分析；
5. 支持主动预警，例如库存风险、交付风险、费用异常、功率达标风险。

关键边界：

1. 管理建议必须基于确定性事实和已固化口径；
2. 预测类能力必须明确模型、数据范围、置信度和不可用边界；
3. 不把 LLM 生成的推测当作经营事实。

### 14.1 每个业务域的必备资产

2. LLM 直接业务事实计算放行：0；
3. 非白名单 SQL/工具调用放行：0；
4. 空结果自动放宽条件：0；
5. 明确 unsupported 被转成成功回答：0；
6. 真实密钥、连接串、生产账号输出：0；
7. 每轮阶段越界开发：0；
8. 核心业务样例回归通过后才允许验收。

## 十五、主要风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 把愿景当现状 | 看到目录或文档就认为能力已具备 | 每轮先审查当前代码和测试结果 |
| 多 Agent 过早失控 | Agent 自由调工具、自由查库、自由写结果 | 先建 capability/tool 白名单与审计，再做编排 |
| LLM 事实漂移 | LLM 编造数字、改写业务结果 | 数值锁定、事实白名单、回答校验、fallback |
| 多域边界混乱 | 一个 planner 里堆所有业务逻辑 | 领域 adapter + shared contract + domain service 分层 |
| 第三方源库风险 | 实时查生产、全量导出、泄露账号 | 只读、小样本、同步中间库、脱敏日志 |
| 文档漂移 | 历史文档与当前状态不一致 | CURRENT_STATUS/NEXT_TASK 主导，旧文档归档或标注 |
| 测试不足 | 只做演示题，未跑全量回归 | 每域建立验收题集与自动化回归 |
| 经营分析口径不清 | 指标名简单但业务定义复杂 | 先做指标口径确认，再开发计算与回答 |

## 十六、最终结论

项目的长期方向不是单点问答系统，而是：

```text
以智能助手为统一入口，
以四大业务域为确定性能力核心，
以 Query Planning 和多 Agent 为调控层，
以中间库、语义目录、工具注册和第三方平台同步为数据与工具底座，
以业务化回答、审计回放和测试集为质量保障，
逐步建设经营计划综合智能平台。
```

推荐执行策略是：

1. **短期**：尊重当前阶段边界，完成物管 SAP MID M2 和计划/物流既有能力回归；
2. **中期**：形成统一业务问答入口、Query Planning、多域路由和受控 NL2SQL/计算引擎；
3. **长期**：在工具注册和审计成熟后，建设多 Agent 编排、第三方平台自动取数分析、经营预警和主动报告能力。

最重要的建设原则是：

```text
先确定性，后智能化；
先可审计，后自动化；
先单域稳定，再多域协同；
先工具受控，再 Agent 编排；
先业务事实准确，再追求回答体验。
```
