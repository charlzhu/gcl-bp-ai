# P0 子里程碑 C：fallback 平台边界固化

## 一、文件用途

本文件用于固化平台主线 `P0` 子里程碑 C 的最小规范，重点回答：

1. 为什么 `fallback` 不是平台默认能力。
2. 第二业务域接入时，为什么默认不继承 `logistics fallback`。
3. 如果未来某个业务域要启用 `fallback`，最少要先声明哪些边界。
4. 是否需要后续追加最小代码守卫，以及为什么。

本文件只做书面边界和最小规范，不做 `fallback` 代码实现或语义清理。

---

## 二、当前平台结论

### 1. `fallback` 当前仍属于 logistics 域特有兼容能力

当前仓库中的 `fallback` 依赖：

- `InMemoryLogisticsQueryRepository`
- `CoreQueryService`
- `CompareService`
- logistics 域专属的过滤、分组和明细字段映射

这意味着：

1. `fallback` 当前不是平台通用兜底引擎。
2. `fallback` 当前不能被视为“所有业务域天然拥有的能力”。
3. 当前 `fallback` 的正确定位是：**logistics 域在数据库链路不可用时的兼容结果机制**。

### 2. 第二业务域默认不继承 `fallback`

平台层的默认原则应明确为：

> 第二业务域接入时，默认按“无 fallback 继承”处理。

原因：

1. `fallback` 当前深度绑定 logistics 数据结构和语义映射。
2. 不同业务域的“降级结果是否可信”不能直接复用物流域经验。
3. 如果默认继承，第二业务域很容易在未声明边界时输出语义误导结果。

---

## 三、第二业务域默认策略

### 1. 默认策略

对于 `plan_bom / business_analysis / material_management` 等后续业务域，当前平台默认策略应为：

- `fallback_enabled = false`
- `fallback_history_enabled = false`
- `fallback_notes = 未声明前不可启用`

### 2. 默认行为

若第二业务域未显式声明 `fallback`，平台默认应理解为：

1. 数据库或正式执行链路不可用时，应返回明确失败或未就绪状态。
2. 不得自动套用 logistics 域的兼容仓储、过滤映射或结果拼装逻辑。
3. 不得因为“平台里已有 fallback”就默认为该域生成兼容结果。

### 3. 当前推荐结论

当前阶段最重要的不是让更多业务域拥有 `fallback`，而是：

1. 先明确 `fallback` 不是平台默认能力；
2. 再明确哪些域如果未来要启用 `fallback`，需要先声明边界；
3. 最后才讨论是否值得抽象成平台级能力。

---

## 四、fallback 启用前必须声明的 4 类边界

任何业务域若未来要申请启用 `fallback`，至少要先补齐以下 4 类声明。

### 1. 数据来源声明

必须明确：

- fallback 数据来自哪里
- 数据更新时间和覆盖范围
- 是正式数据、历史快照，还是 demo / 兼容样本
- 与主执行链路相比，缺了哪些字段或维度

若这部分说不清，则不应启用 fallback。

### 2. 语义可信范围声明

必须明确：

- fallback 支持哪些查询模式
- 支持哪些过滤条件
- 支持哪些维度
- 哪些结果只能视为“近似兼容结果”
- 哪些业务语义严禁通过 fallback 输出

示例：

- logistics 当前明确禁止把“基地”冒充成“承运商/物流公司”。
- 对第二业务域，也应提前列出同类“严禁误映射”的语义清单。

### 3. 状态展示方式声明

必须明确：

- fallback 结果在前端如何展示
- 状态码是否显示为 `FALLBACK_MODE`
- 何时由 `EMPTY_RESULT` 优先覆盖
- 是否必须展示 `compatibility_notice`
- 是否需要额外展示“当前结果不是正式执行链路结果”的警示

若没有明确状态展示方式，fallback 容易被业务误认为正式结果。

### 4. 是否进入历史回放声明

必须明确：

- fallback 结果是否允许写入历史列表
- fallback 结果是否允许进入详情回放
- 历史详情中如何标识它是 fallback 结果
- 是否允许后续通过“重新查询”回放这类记录

当前建议：

- 即使允许进入历史，也必须带上清晰的 `execution_mode=fallback` 与提示信息；
- 未声明前，默认不应把 fallback 视为与正式执行结果同等级的历史记录。

---

## 五、对域接入规范的固化要求

第二业务域接入规范中，建议至少固化以下规则：

### 1. 域注册最小字段新增约束

域注册信息至少应支持表达：

- `fallback_enabled`
- `fallback_history_enabled`
- `fallback_notes`

推荐默认值：

- `fallback_enabled = false`
- `fallback_history_enabled = false`
- `fallback_notes = 未声明前不可启用`

### 2. 第二业务域接入清单新增约束

若某个业务域计划启用 fallback，则在“第二业务域接入最小清单”中必须额外补齐：

1. fallback 数据源说明
2. fallback 语义可信范围
3. fallback 状态展示方案
4. fallback 是否进入历史回放

若这 4 项未补齐，则该域即便其他资料已齐，也不应默认打开 fallback。

---

## 六、对前端和历史详情的影响说明

### 1. 对前端的影响

这次边界固化不会直接改前端代码，但它会影响后续平台实现原则：

1. 前端不能把“有结果”简单理解成“正式执行结果”。
2. 若未来某域启用 fallback，前端必须看到明确状态和提示。
3. 若某域未启用 fallback，前端不应收到隐式兜底结果。

### 2. 对历史详情的影响

这次边界固化不会直接改历史页，但它明确了后续要求：

1. fallback 记录若进入历史，必须能被明确识别。
2. 历史详情里应能看出该记录是正式链路还是兼容链路。
3. 未显式声明前，第二业务域不应默认把 fallback 结果写进可回放历史。

---

## 七、最小守卫策略建议

### 1. 是否建议增加最小代码守卫

建议。原因不是为了立刻扩实现，而是为了防止后续第二业务域通过复制 logistics 代码路径，**无意识继承 fallback**。

如果只有文档约束，没有任何最小守卫，后续最容易出现的风险是：

1. 新域在未声明边界时默认走了 fallback；
2. 日志和历史页把 fallback 结果当正式结果记下来；
3. 业务误以为该域已具备完整降级能力。

### 2. 推荐的最小守卫方向

后续若进入实现阶段，建议只加最小守卫，不做大重构：

1. 域注册默认 `fallback_enabled = false`
2. 只有显式声明的域才允许走 fallback
3. fallback 响应必须带：
   - `execution_mode = fallback`
   - 明确状态码
   - `compatibility_notice`
4. 未显式声明 `fallback_history_enabled` 前，默认不把 fallback 记录作为平台默认回放能力

### 3. 当前阶段的结论

当前阶段只需要先把这些守卫要求写清楚，**不需要现在就实现**。

---

## 八、本轮结论

### 1. 当前边界结论

- `fallback` 当前属于 logistics 域特有兼容能力，不属于平台默认能力。
- 第二业务域默认不继承 `fallback`。
- 若未来某域要启用 `fallback`，必须先声明数据来源、语义可信范围、状态展示方式、是否进入历史回放。

### 2. 当前明确不做

本轮不做：

1. fallback 全量语义清理
2. compare / detail 共享字段补齐
3. 第二业务域代码开发
4. RAG / 工具层 / Agent 实现

### 3. 后续衔接建议

若后续要进入 fallback 平台级守卫实现，应优先按“最小守卫”方式处理，而不是先抽象通用 fallback 引擎。
